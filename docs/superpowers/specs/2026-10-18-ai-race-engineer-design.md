# AI 比赛工程师（实时问答）设计文档

- 日期：2026-10-18
- 目标版本：v1.4.3（第一期）
- 状态：待批准

## 一、意图与动机

现在的小小领航员是「机械回答」：语音 → 短语库精确匹配 → 意图 → 硬编码规则 → 拼接录音。它有三个天花板：

1. **只认预设问法。** 短语库阈值 0.66，实测「刚才那个弯为什么慢了 0.3 秒」最高分只有 **0.47**，在**短语库这一步就没命中**，直接播「没听清」——根本进不到路由层。即使侥幸命中意图，「为什么/分析」也会被 `router.route()` 的硬拒绝挡掉。
2. **回答是录音素材。** 无法组合出新句子。
3. **不会推理。** 只做「读字段 → 比阈值 → 播录音」，不能跨数据思考。

用户希望它向「真正的比赛工程师」靠近：**在比赛中随时提问，基于当下与近期赛况得到分析性回答。**

明确的范围边界：**只做比赛中实时问答。** 不做赛后回看分析、不做多轮对话。

### 实测结论（决定了架构）

对现有短语库跑过旗舰问句，结果如下：

| 问句             | 短语库结果                            |
| -------------- | -------------------------------- |
| 刚才那个弯为什么慢了0.3秒 | **无意图**，最高分 0.47 < 0.66          |
| 帮我分析一下我的圈速     | 无意图，0.46                         |
| 我为什么进弯推头       | 无意图，0.48                         |
| 现在什么策略         | 无意图（名次与旗号只差 0.01，边界拒绝）           |
| 我该不该进站         | 命中 `query_pit`（1.00），规则层**答得上来** |

反向问题同样存在：`圈速稳定吗` / `我慢在哪` / `成绩怎么样` 都能命中 `query_laptime`，但规则层统一播同一条 `SPCC_DOBETTER`——**答了但答非所问，且不会触发任何「答不了」**。

**架构含义**：档位规则不能建立在「intent 是否命中」上，因为最想要的问句压根没有 intent。必须在路由**之前**引入独立的「问题分类预检」。详见第五节。

## 二、目标与非目标

### 目标

- 比赛中随时提问，能回答**需要跨数据推理**的问题（为什么慢、该不该进站、现在什么策略）。
- 规则层继续作为默认主力：**毫秒级、零成本、离线可用、绝不猜**。
- **模型由用户自己接**：软件提供 OpenAI 兼容的 API 接入口，不绑定任何厂商。
- **软件自身的响应速度有硬保障**，不因用户接了慢模型而退化。
- 失败时明确降级：宁可说「现在来不及算」，也不胡说。
- **赛后复盘**：确认正确的问答沉淀进学习库，下次复用（省延迟、省成本）。

### 非目标（本期不做）

- **赛后数据分析**（遥测回看、圈速对比、.ibt 文件导入、跨场次统计）——注意：本期的「赛后复盘」只针对 **AI 问答的正确性确认**，不涉及遥测数据分析。
- 多轮追问、主动播报。
- 替换或削弱现有规则层。
- 内置任何厂商的 API Key 或代为付费。
- 语音克隆 / 音色训练 / 自制音色。

### 反目标（即便技术上跑通也算失败）

- 断网或没配 Key 时软件变得不可用。
- 规则层被绕过，导致比赛中延迟普遍上升。
- 模型编造遥测里没有的数字，并被用户当真。
- 用户接入慢模型后，整个软件变得卡顿或不可用。
- API Key 泄漏到日志、界面或仓库。

## 三、约束

- **延迟**：见「六、响应速度保障」的硬约束。
- **网络**：由用户自己的模型服务决定；不可用时功能自动禁用，不影响原有功能。
- **成本**：由用户自行承担；软件只负责控制上下文规模。
- **平台**：Windows（PyInstaller 打包），Python 3.12。
- **红线**：现有「绝不猜」原则在规则层不变；模型层的幻觉必须被程序侧校验拦住。

## 五、三档模式（核心产品设计）

三档表达的是「模型接管范围」，而非「是否守底线」。**安全类硬拒绝在所有档位都生效。**

### 5.1 问题分类预检（`query_class.py`，新增，必须先于路由）

**为什么不基于 intent**：实测旗舰问句（「刚才那个弯为什么慢了 0.3 秒」）在短语库阶段就没命中（0.47 < 0.66），`intent is None` 时根本不进 `router.route()`。若档位规则依赖 intent，C 档永远够不到这类问题。

因此新增**独立的分类预检**，只依赖问题文本，与意图识别并列、先于它执行：

```python
class QueryKind(str, Enum):
    SAFETY = "safety"          # 操作车辆 / 解释处罚 / 范围外
    ANALYSIS = "analysis"      # 为什么、什么原因、分析、怎么看、评价
    KNOWN = "known"            # 命中短语库且是事实型问题
    UNKNOWN = "unknown"        # 未命中，且不含分析词
```

判定顺序（先安全后其他，一旦命中即返回）：

1. `SAFETY`：命中安全词表 → 直接拒绝，任何档位都不转模型
2. `ANALYSIS`：命中分析词表（为什么/什么原因/分析/评价/怎么看/哪里慢/该怎么跑）→ 归为分析型
3. `KNOWN`：短语库命中且意图不在分析范畴
4. `UNKNOWN`：以上都不是

**注意 `SAFETY` 与 `ANALYSIS` 的词表有重叠**（「为什么被罚」既是「为什么」又是处罚解释），因此**必须先判 SAFETY**。

### 5.2 安全类硬拒绝（不可越过）

与现有 `router.route()` 的立场一致，任何档位都不放行：

- **操作车辆**：「替我开」「帮我关」「调高/调低/调到/改成/设置为」「怎么开」「怎么办」
- **解释处罚原因**：「处罚是什么」「为什么被罚」「怎么判」「会被罚」
- **遥测范围之外**：时间/日期、备胎库存等

判定标准：**「要求软件做超出现有能力的动作，或解释规则/处罚」**。仅询问数据状态（哪怕数据缺失）不属于安全类。

### 5.3 三档与分类的对应关系

| 分类             | A 档     | B 档（分析键） | C 档（默认）                |
| -------------- | ------- | -------- | ---------------------- |
| `SAFETY`       | 拒绝      | 拒绝       | 拒绝                     |
| `ANALYSIS`     | **转模型** | **转模型**  | **转模型**                |
| `KNOWN`（规则答得上） | 规则播录音   | 规则播录音    | 规则播录音                  |
| `KNOWN`（规则答不了） | **转模型** | 规则播「答不了」 | 若意图在白名单则**转模型**，否则规则拒绝 |
| `UNKNOWN`      | **转模型** | 规则播「没听清」 | 规则播「没听清」               |

**C 档为什么连 `ANALYSIS` 也放行**：分析型问题本身就是最该交给模型的一类，且它不需要 intent 就能识别。这是修复旗舰用例不可达问题的关键。

B 档不接管 `UNKNOWN`：分析键是显式动作，用户按下它说明想问的是分析型问题；没听懂就照实说没听懂。

### 5.4 各档行为细节

**C 档（默认）**：只对 `ANALYSIS` 分类，以及白名单意图下的 `KNOWN` 无解情况转交模型。白名单：

- `query_laptime`、`query_pit`、`query_fuel`、`query_gap`、`query_opponent`、`query_weather`、`query_damage`

**不含** `query_flags`（规则答得准）；**不含** `UNKNOWN`（不花 2 秒猜）。

**A 档**：除 `SAFETY` 外全部转交，**包括 `UNKNOWN`**。受限流与自适应降级约束。此时无法预知问题类型，上下文必须给通用全量（`now + derived + 最近 5 圈`），token 预算按上限走。

**B 档（分析键）**：规则照常全权处理 PTT。用户按住**专用分析键**提问时，跳过「规则是否答得上」的判断，直接按分析型走模型（`SAFETY` 仍先拦）。

### 5.5 已知的「答了但答偏」（本期不解决）

以下问法规则层会「成功」作答但答非所问，**不会触发模型接管**：

- `圈速稳定吗` / `我慢在哪` / `成绩怎么样` / `有没有进步` → 都命中 `query_laptime`，统一播 `SPCC_DOBETTER`
- `最近几圈圈速` → 播的是**上一圈**成绩
- `进站窗口在哪` / `现在进站划算吗` → 播 `SPCC_FUELFINRACE`

**本期处理**：不覆盖规则层已成功的回答（避免每次提问都花 2 秒）。但要把这些说法**补进 `query_class` 的 `ANALYSIS` 词表**（如「慢在哪」「稳定吗」「有没有进步」），让它们走分析路径而非规则路径。其余命中后答偏的情况，记入日志供二期优化。

### 5.6 拒绝类型的实现方式

现有 `Decision` 只有自由文本 `reason`，且 `refusal_msg` 已被「换一条拒绝音」占用，不能复用。

**本期方案**：新增 `Decision.kind: str = "ok"`（取值 `ok / safety / capability / state`），只在**需要跨模块判定**的少量位置填充；`query_class` 负责文本级分类，两者互补：

- `query_class` 判定「该不该转模型」（文本级，先于路由）
- `Decision.kind` 判定「路由为什么拒绝」（执行级，路由内部）

不给全部 60+ 处 `_refuse()` 调用都补 `kind`（改动面太大、易与现有 132 个测试冲突）。只在 `router.route()` 的 5 个前置分支与各意图函数的**无条件拒绝**处标注。

按键绑定复用现有的按键采集 UI，与 PTT 分开配置（`ai.analysis_key`）。**默认不绑定**，避免与游戏内按键冲突。

**首次使用引导（必做）**：用户第一次启用 AI 功能（或选择 B 档）时，界面弹出引导，要求采集一次分析键才能完成配置。引导需说明：

- 这个键只用于「按住提问、走 AI 分析」，与 PTT 是两套按键
- 采集前请先确认该键在 iRacing 里没有绑定其他功能
- 采集失败或跳过时，B 档保持不可用（灰显），并说明原因

不允许出现「B 档已选但键没绑、按了没反应」的状态——要么引导完成绑定，要么 B 档明确不可用。

## 六、响应速度保障（硬约束，代码内强制）

### 6.1 先明确能做到什么

**软件无法让一个慢模型变快。** 本设计保证的不是「任何模型都在 2 秒内答完」，而是：

> **无论用户接入什么模型，软件自身的响应路径永远不会因模型而变慢或卡死。**

具体表现：规则层照常毫秒级出结果；模型超时立刻砍掉并给出明确提示；用户不会经历「按了没反应」或「界面卡住」。

### 6.2 双轨时间预算

规则层与 AI 路径是两条独立的轨，互不占用预算。

| 轨道       | 层级         | 预算          | 说明                   |
| -------- | ---------- | ----------- | -------------------- |
| **规则轨**  | 规则层全流程     | ≤ 50 ms     | 命中即播录音，模型与 TTS 完全不参与 |
| **AI 轨** | LLM 首字     | ≤ 1.5 s     | 超过视为本次不可用            |
|          | LLM 全答     | ≤ 2.0 s     | 硬截止，到点主动取消请求         |
|          | TTS 合成     | ≤ 1.5 s     | 独立硬截止，到点放弃语音、保留文字    |
|          | **AI 轨合计** | **≤ 3.5 s** | 两环各自封顶，互不吃对方时间       |

**关键设计**：LLM 与 TTS 各留独立截止，慢的一环不会挤占另一环。TTS 超时只丢声音、文字照常显示，用户不会失去答案。

### 6.3 代码内强制（配置只能收紧，不能放宽）

以下写在代码常量里；`config.yaml` 只能设得更小，设更大时被钳制并在日志告警：

- `LLM_DEADLINE_HARD_MAX = 2.0s`
- `TTS_DEADLINE_HARD_MAX = 1.5s`
- `AI_TOTAL_DEADLINE_HARD_MAX = 3.5s`
- `MAX_INPUT_TOKENS_HARD = 1500`
- `MAX_OUTPUT_TOKENS_HARD = 300`
- `SINGLE_INFLIGHT = True`（同一时刻只允许一个 AI 请求，新请求取消旧请求）

### 6.4 永不阻塞的四条规则

1. **规则先行**：规则层能答的问题，永远不进入模型路径（B 档分析键除外，那是用户显式要求）。
2. **立即反馈**：需要模型时立刻返回「正在分析」，界面不空等。
3. **硬性取消**：到截止时间主动 abort HTTP 请求，不赌「可能马上回来」。
4. **上下文裁剪**：超预算时先砍远圈、再砍对手细节，保证输入 token 不成为延迟主因。

### 6.5 连接与预热

- 复用 HTTP 连接（keep-alive），避免每次重新 TLS 握手
- 启动后与首次提问前各发一次极小预热请求（`max_tokens=1`）
- 记录每次往返延迟，供自适应降级判断

### 6.6 自适应降级

- 记录最近 10 次调用延迟
- **连续 3 次超时**，或 **p90 > 1.8 s** → 自动关闭模型路径，界面提示「当前模型太慢，已暂时关闭 AI 分析」
- 用户可手动重试恢复；恢复后重新统计

### 6.7 明确不承诺

- 不承诺第三方模型的可用性、准确率或输出格式
- 不承诺网络抖动下的延迟
- 不承诺超出预算的复杂分析（宁可说「来不及算」）

## 七、数据层：从「瞬时快照」到「分层缓冲」

### 现状

`TelemetrySampler` 已以 60Hz 持续采样（`telemetry.py:488`），`DerivedTracker` 维护油量中位数、差距 6 秒窗口。**池子只有当下，没有历史。**

### 实现归属：扩展现有 `DerivedTracker`，不新开并列类

**不新增并列 tracker。** 理由：`DerivedTracker` 已经有一套完整的「圈边界 + 有效圈」判定（session 变更/回退/进车库/圈号倒退就 `reset()`，`_valid_lap` 在进站/加油/跨线三处置假，油耗只接受 `lap == _last_lap + 1`）。另开一个类会让「有效圈」出现两个定义，长期必然漂移。

**做法**：在 `DerivedTracker` 内扩展，暴露公共接口：

- `record_lap(summary, trace=None)`：圈边界时调用，`trace` 本期恒为 `None`（二期填轨迹）
- `lap_records: list[dict]`：环形缓冲，保留最近 20 圈
- `valid_lap` 从私有 `_valid_lap` 提升为公共属性，供记录判定

**有效圈的语义要放宽**（现有 `_valid_lap` 是为油耗样本设计的，过于严格）：

| 情况         | 油耗样本可用 | 圈速/胎温记录可用       |
| ---------- | ------ | --------------- |
| 进站加油圈      | 否      | **是**（圈速和胎温仍有效） |
| 跨线时在维修区    | 否      | 否（圈速含维修区时间）     |
| 圈号非连续      | 否      | 否               |
| session 重开 | 否      | 否               |

即：**油耗与圈记录用两套判据**，不能共用一个标志。

**接入点**：`TelemetrySampler._loop` 目前只调一次 `self.tracker.update(snap)`。扩展后仍在 `update()` 内部完成圈记录写入，**必须排在 `_derive_gaps()` 之后**，否则圈末记录的 `gap_ahead_s` 是上一帧的值。

### sim 模式下测不到圈边界

`SimTelemetry.read()` 里 `lap=12` 是常量，永远不递增——`--sim` 跑多久都产不出圈记录。

**处理**：给 `SimTelemetry` 加一个可选的「圈推进」模式（如每 8 秒模拟一圈推进），**默认关闭**，只在 `--sim-advance` 参数下开启。这样：

- 现有 132 项测试不受影响（默认行为不变）
- 需要测圈记录的用例显式开启
- 其余被测场景（构造 Snapshot 序列）不依赖 sim

### 数据字段

在每圈边界（`lap` 递增）写一条聚合记录，环形缓冲保留最近 **20 圈**：

```python
{
  "lap": 13,
  "lap_time": 83.512,
  "fuel_start": 18.4,
  "fuel_used": 1.42,
  "tyre": {"LF": {"temp": 92.1, "wear": 0.87}, ...},
  "position": 4,
  "class_position": 3,
  "gap_ahead_s": 1.8,
  "gap_behind_s": 1.2,
  "flags": ["green"],
  "in_pit": false,
  "air_temp": 28.0,
  "track_temp": 41.0,
  "wetness": 1,
  "incidents": 2,
}
```

**只记录有效圈**：见上表判据。

### 派生摘要（给模型用）

- 最近 3/5/10 圈平均圈速、标准差
- 圈速趋势（变快或变慢）
- 油耗趋势
- 胎温趋势（每轮）
- 名次变化
- 前后车差距变化

### 本期能力边界（必须写进提示词与验收标准）

本期数据层**只到圈级聚合**，没有弯道分段、没有速度轨迹。因此模型能回答的是：

- ✅ 「这圈 83.5 秒，比上圈慢 0.4 秒；胎温升了 6 度，油量正常」
- ✅ 「最近三圈在变慢，平均每圈慢 0.3 秒」
- ❌ 「第七弯刹车晚了」——**答不了**，必须明确说「读不到弯道数据」

提示词中必须写明：**只知道每圈的汇总数据，不要假装能定位到具体弯道**。

### 第二期扩展位（本期不实现，但预留接口）

弯道级归因需要「时间-距离轨迹」：60Hz 采样 `LapCurrentLapTime` 与赛道位置，存成 `(distance_pct, lap_time)` 序列，再与参考圈逐段对比。

本期预留：

- `DerivedTracker.record_lap(summary, trace=None)` 形式设计，`trace` 参数本期恒为 `None`
- 不启动高频环形缓冲，避免本期承担 CPU 与内存成本
- 第二期只需填入 `trace` 并扩展 `race_context` 的裁剪逻辑，不改上层调用结构

### 并发模型（关键实现约束）

现有 `Assistant.ask()` 整体被 `@exclusive` 持锁，且 `Player.play*` 是 `blocking=True`。**若模型调用留在 `ask()` 内，等待模型的 1–2 秒里麦克风全程是聋的**，「新请求取消旧请求」根本无从触发。

因此本期必须：

- `ask()` 只负责规则层，**模型调用移出 `_operation_lock`**
- `busy` 标志不覆盖模型等待期，分析键可随时打断重问
- 单飞约束下沉到 `llm_engine` 内部（模块级锁），而非依赖上层的 `exclusive`
- 规则层播报期间按分析键：**忽略**（沿用现有 `is_busy` 语义），不打断续播

这样语音侧才能真正做到「新问题取消旧请求」。

## 八、上下文组装（`race_context.py`）

按问题类型组装紧凑 JSON，控制在 **1500 token 以内**：

```python
{
  "now": { ... 瞬时关键字段 ... },
  "recent_laps": [ ... 最近 N 圈 ... ],
  "derived": { ... 预计算好的展示值 ... },
  "session": { ... 总圈数、剩余、旗号 ... }
}
```

- 简单问题：只给 `now` + `derived`
- 分析型问题：`now` + `recent_laps`（最近 5 圈）+ `derived`
- 对手类问题（`query_gap` / `query_opponent`）：额外给 `opponents` 层（见下）
- 超预算时裁剪顺序：**先丢远圈（由远及近）→ 再丢 `opponents` 里的非邻车字段 → 再丢 `derived` 的对手字段 → 最后只剩 `now` + `session`**；token 用字符数估算，不引入 tokenizer 依赖

### 对手数据必须单独成层

`query_gap` 与 `query_opponent` 依赖 `car_last_laps` / `car_best_laps` / `car_completed_laps` / `car_positions` / `car_est_times` / `car_lap_dist` 这一整组数组。若上下文不带这些，这两条白名单意图的模型回答永远只能是「读不到」，等于白放两条死条目。

但全量数组有 20+ 台车 × 6 个字段，token 会爆。因此：

```python
"opponents": {
  "ahead":  {"pos": 3, "gap_s": 1.8, "last_lap": 83.2, "best_lap": 82.8, "completed": 12},
  "behind": {"pos": 5, "gap_s": 1.2, "last_lap": 84.1, "best_lap": 83.9, "completed": 12},
  "leader": {"pos": 1, "last_lap": 82.5, "best_lap": 82.1, "completed": 13},
  "field_size": 18
}
```

**只带前后邻车 + 领跑者共 3 台**，约 120 token。其他车手不进入上下文。

### 关键：派生值必须预计算并四舍五入

数字闸只接受**原样引用**上下文里已有的数值（见第十一节），模型自己算出来的数会被判失败。因此以下派生量必须在组装时算好、并按口语习惯四舍五入：

| 派生量      | 示例                                  |
| -------- | ----------------------------------- |
| 油量可跑圈数   | `laps_of_fuel: 6.2`                 |
| 油量富余圈数   | `laps_spare: 1.2`                   |
| 与最佳圈差值   | `delta_to_best: 0.4`                |
| 最近 3 圈均值 | `avg3: 83.6`                        |
| 圈速趋势     | `trend_per_lap: 0.3`                |
| 胎温变化     | `tyre_temp_delta: {"LF": 6.0, ...}` |


提示词必须写死：**只准引用上下文中给出的数值，不要自己计算**。

## 九、模型调用层（`llm_engine.py`）

### 接口：OpenAI 兼容，用户自填

**不绑定任何厂商。** 用户填 `base_url` / `api_key` / `model`，软件按 OpenAI Chat Completions 协议调用。国内主流厂商与本地推理大多兼容这一格式。

### 预设（只是预填默认值，用户可改）

| 预设        | base_url                                   | 示例 model         |
| --------- | ------------------------------------------ | ---------------- |
| DeepSeek  | `https://api.deepseek.com`                 | `deepseek-chat`  |
| 火山方舟      | `https://ark.cn-beijing.volces.com/api/v3` | 用户填接入点 ID        |
| 月之暗面      | `https://api.moonshot.cn/v1`               | `moonshot-v1-8k` |
| 本地 Ollama | `http://127.0.0.1:11434/v1`                | `qwen2.5:7b`     |
| 自定义       | 用户填                                        | 用户填              |

### 兼容性处理

- **不支持 JSON mode** → 退回「提示词要求 JSON + 程序侧解析 + 失败重试」
- **不支持流式** → 退回一次性返回（延迟更高，但仍受硬截止约束）
- **返回格式异常** → 降级

### 连接自检（界面「测试连接」按钮）

发一条最小请求，报告：连通性、往返延迟、是否支持流式、是否支持 JSON mode。用户装完就能判断自己接的模型够不够快。

### 系统提示词要点

- 你是 iRacing 比赛工程师，只能基于提供的遥测数据回答
- 数据里没有的，明确说「现在读不到」，不要推测
- 回答简短口语化，不超过 60 字
- 不解释推理过程，直接给结论
- 不提供调校或操作指令，不解释处罚原因

### 输出契约（强制 JSON）

```json
{
  "answer": "你的油还够跑 6.2 圈，比赛还剩 5 圈，不用进站。",
  "confidence": 0.9,
  "refused": false,
  "data_used": ["laps_of_fuel", "laps_remain"]
}
```

### 不重试（修正）

**非法 JSON 不重试，直接降级。** 理由：单次 `timeout_s=2.0`，重试一次最坏 4.0s，必然突破 3.5s 总预算。用 `response_format={"type":"json_object"}`（服务支持时）降低概率；不支持时靠提示词强约束 + 程序侧解析，失败即降级。

## 十、语音路径的反馈形态（关键，必须先定）

### 问题

模型答出的是**新句子**，语音包里没有对应录音。语音路径下用户听完 PTT 后，若什么都不播，会以为软件坏了。

### 本期方案：新增一条固定提示音

向语音包追加**一条新素材**（走现有的 `content/` + `scripts/tts_doubao.py` 合成流程），文字建议：

> 「答案在屏幕上。」

行为规则：

| 场景             | 语音反馈            | 屏幕     |
| -------------- | --------------- | ------ |
| 规则层命中          | 播录音（不变）         | 不变     |
| 转模型且**已配 TTS** | TTS 合成播放        | 显示文字   |
| 转模型、**未配 TTS** | 播「答案在屏幕上」+ 显示文字 | 显示文字   |
| 转模型、模型失败/超时    | 播现有「答不了」话术      | 显示失败原因 |

### 实现影响（必须在交付清单里）

新增素材会牵动：

1. `content/assistant-telemetry-v1.x.json` 追加条目（新 msgId，如 `AST_AI_SEE_SCREEN`）
2. `scripts/synthesize_telemetry.py` 重新合成该条
3. 语音包版本号与 `build_dist.py` 的素材校验清单
4. 132 项测试里涉及素材数量的断言（如 `check_pack` 的 851 msgId / 3,074 条）

**这是本期唯一的语音包改动**，其余音频一律不动。

## 十一、语音合成层（`tts_engine.py`，可选）

### 10.1 定位

**可选层，默认关闭。** 未配置时行为与「只出文字」完全一致：文字照常显示，不发声。

用户自填接入参数，软件不内置任何厂商凭据、不预设音色。

### 10.2 两种适配器

| 适配器           | 协议                                                                                  | 典型服务                           |
| ------------- | ----------------------------------------------------------------------------------- | ------------------------------ |
| **豆包（v3）**    | `POST openspeech.bytedance.com/api/v3/tts/unidirectional`，NDJSON 流式，音频 base64 分段    | 火山引擎豆包语音合成                     |
| **OpenAI 兼容** | `POST {base_url}/audio/speech`，请求体 `{model, input, voice, response_format}`，返回二进制音频 | OpenAI TTS、多数第三方兼容服务、本地 TTS 网关 |

复用现有 `scripts/tts_doubao.py` 的合成实现（`synthesize()` 已处理好 NDJSON 解析与错误码），移入运行时模块并做参数化。

### 10.3 音频格式与播放

- 合成结果优先请求 **16-bit PCM WAV**，避免运行时转码依赖
- 服务只返回 mp3 时，用现有的 ffmpeg 依赖转码（打包版已带 `imageio_ffmpeg`）
- 合成结果写入内存缓冲后交给现有 `Player.play_many()` 播放路径
- **不落盘**（避免比赛中大量临时文件）

### 10.4 硬约束

- 合成硬截止 **1.5 秒**，到点放弃语音、保留文字
- 单飞：同一时刻只允许一个合成请求
- 失败不重试（实时场景重试等于超时），直接降级为「只出文字」
- 峰值音量沿用现有播报流程的响度处理，避免 TTS 与录音音量不一致

### 10.5 与录音路径的关系

| 场景                    | 输出                           |
| --------------------- | ---------------------------- |
| 规则层命中                 | **播录音**（现有 msgId 音频），不经过 TTS |
| 规则未命中 + 模型回答 + 已配 TTS | 模型文字 → TTS → 播放              |
| 规则未命中 + 模型回答 + 未配 TTS | 只显示文字                        |
| TTS 超时/失败             | 显示文字，不发声，界面标注「语音合成失败」        |

**规则层永远优先使用录音**，这是音色一致性和零延迟的保障。TTS 只服务于模型生成的新句子。

### 10.6 界面配置项

- 适配器选择：豆包 / OpenAI 兼容 / 关闭
- 豆包：`api_key`、`speaker`（音色 ID）、`resource_id`、可选 `speech_rate`
- OpenAI 兼容：`base_url`、`api_key`、`model`、`voice`、`response_format`
- 「测试合成」按钮：合成一句固定短句并播放，报告耗时与是否成功
- 音色说明：明确提示音色与现有录音包不同，属预期行为

## 十二、三道校验闸（防幻觉核心）

模型返回后依次校验，**任一道不通过即降级为「答不了」**：

### 1. 长度闸

`answer` 超过 `max_answer_chars`（默认 60，**硬上限 60**）→ 拒绝（不截断，截断会留下半句话）。

配置只能调小，设大于 60 时被钳到 60 并在日志告警。

### 2. 数据闸

`data_used` 中每个字段名必须真实存在于本次给模型的上下文里。出现不存在的字段 → 拒绝。

### 3. 数字闸

从 `answer` 提取所有**阿拉伯数字**（含小数），每个数字必须能在上下文中找到匹配值。

**中文数字不识别，也不通过**——出现「五圈」「一点八秒」即拒绝。理由：中文数字解析歧义大，容易成为绕过闸门的口子。提示词必须写死「用阿拉伯数字」。

**模型只能原样引用上下文里给出的数值**，因为容差极窄。所有需要展示的派生值必须在 `race_context` 里预计算好（见第八节）。

#### 容差

| 类型   | 容差    |
| ---- | ----- |
| 整数   | ±0.05 |
| 一位小数 | ±0.06 |
| 百分比  | ±0.5  |
| 圈速分秒 | 见下    |

#### 必须支持的换算（否则白名单第一条 `query_laptime` 必然被打死）

模型说「上一圈 1 分 23 秒 5」，上下文是 `lap_last: 83.512`。这是**最常出现的表述**，必须建模：

- **秒 → 分秒**：把分数的总秒拆成 `分*60 + 秒`，再分别与候选值比对
- 允许的余地：`83.512` → 「1 分 23.5」或「1 分 24」均可（分秒拆解后，秒部分容差 ±0.6，因为口语常四舍五入到整秒）
- 若模型给出的分秒**拆解后对不上任何候选值** → 拒绝

#### 百分比缩放

上下文里 `relative_humidity: 0.62`、`tyre wear: 0.87`、`fuel_pct: 0.42` 这类**0–1 比例值**，模型会说「62%」「87%」。闸门须对每个比例字段**同时接受原值与 ×100 值**。

#### 允许例外

- 序数词（第 4 名）：与 `position` 比对
- 中文序数（「第一名」）：不提取
- 来自问题本身的数字（用户问「慢了 0.3 秒」，答案里出现 0.3 可豁免）
- 时间换算（见上）

**对不上 → 拒绝，退回「现在读不到可靠数据」。**

#### 上线前的必须动作

在实现完成后，用**真实模型跑 50 条白名单问句**，统计误杀率。**误杀率 > 20% 视为不合格**，需回头调整 `race_context` 的预计算字段或放宽容差。这个指标写进验收标准。

## 十三、失败与降级

| 情况          | 行为                        |
| ----------- | ------------------------- |
| 未配置 API     | 功能禁用，界面显示「AI 分析未配置」，规则层照常 |
| 网络不可达       | 超时后放弃，返回「现在连不上分析服务」       |
| 模型返回非法 JSON | 重试 1 次，仍失败则降级             |
| 三道校验任一失败    | 降级为规则层的「答不了」话术            |
| 超过限流        | 直接降级并提示「问得太频繁」            |
| 连续 3 次超时    | 自动关闭模型路径并提示，可手动恢复         |
| TTS 超时或失败   | 只显示文字，界面标注「语音合成失败」        |

### 自适应降级的具体规则

- **触发条件**：**连续 3 次**调用超时（不含 p90 判据——10 次里 2 次慢就关太敏感）
- **样本口径**：只有真实提问的调用计入；预热请求与「测试连接」**不计入**
- **恢复方式**：**半开**——用户点「重试」后先放行一次试探调用，成功则完全恢复并清空计数，失败则保持关闭
- **持久化**：关闭状态**不跨重启保留**，重启后重新统计

**原则：任何失败都不阻塞、不崩溃、不改变规则层的正常行为。**

## 十七、赛后复盘与问题学习库

### 17.1 动机

模拟赛车比赛里问题高度重复。走过的模型调用不应该白花——赛后确认正确的问答应当沉淀下来，下次直接复用，省延迟、省成本。

### 17.2 核心安全约束：不能缓存带动态数值的成品答案

大模型回答长这样：「你的油还够跑 **6.2** 圈，比赛还剩 **5** 圈，不用进站。」

这段话只有那一刻成立。直接缓存成录音播出就是**播报过期数据**，违反「绝不猜」红线。

因此**分两类沉淀**：

| 类型 | 例子 | 缓存形式 |
|---|---|---|
| **知识型**（不随比赛变化） | 「蓝旗是什么意思」「什么时候用雨胎」 | 完整问答 + 语音 |
| **动态型**（依赖遥测数值） | 「油够跑几圈」「该不该进站」 | **条件化模板**，不缓存成品 |

### 17.3 动态型的沉淀形式：条件化模板

让模型在生成回答时**额外输出结构化模板**：

```json
{
  "answer": "你的油还够跑 6.2 圈，比赛还剩 5 圈，不用进站。",
  "template": {
    "params": ["laps_of_fuel", "laps_remain"],
    "rules": [
      {"when": "laps_of_fuel >= laps_remain * 1.15",
       "say": "油够跑 {laps_of_fuel} 圈，剩 {laps_remain} 圈，不用进站"},
      {"when": "laps_of_fuel >= laps_remain",
       "say": "油够跑 {laps_of_fuel} 圈，剩 {laps_remain} 圈，很紧"},
      {"when": "true",
       "say": "油只够 {laps_of_fuel} 圈，还要跑 {laps_remain} 圈，得进站"}
    ]
  }
}
```

**程序侧强制校验**（任一不通过则不进入学习库）：

1. `params` 的每个字段必须在 `race_context` 字段白名单内
2. `when` 表达式只能是简单比较（`>=`、`<=`、`>`、`<`、`*`、`+`），**禁止函数调用、禁止访问白名单外字段**
3. 规则必须覆盖 `when: "true"` 兜底分支
4. 每条 `say` 填充后必须能通过数字闸
5. 模板不得包含无法从参数推出的结论

### 17.4 复用方式：自动复用 + 事后纠错

**命中即自动复用，不等用户确认**（用户选择：直接模糊匹配）。

安全网靠「事后纠错」而非「事先确认」：

1. 模糊匹配命中学习库 → 直接用模板重算 + 播报
2. 界面标注「复用 XX 的模板」并显示实际填入的数值
3. 用户可**一键标记「错误」**
4. 模板有**权重**：标记错误 -2，连续错 2 次自动禁用；用户标记正确 +1
5. 禁用模板不再参与匹配，可在设置页手动恢复

### 17.5 赛后复盘界面

设置页新增「AI 复盘」区块：

- 按场次分组，列出所有走过模型的问答
- 每条显示：问题、当时的回答、关键遥测快照、耗时
- 三条操作：**正确**（入学习库）/ **错误**（不入）/ **没帮助**（不入但记录）
- 可批量操作，可导出

### 17.6 存储

`config.local.yaml` 同级的用户数据目录下：

```
<data_dir>/ai_learn/
  knowledge.jsonl      # 知识型问答（问题、回答、语音文件路径）
  templates.jsonl      # 动态型模板（问题、模板、权重、成功/失败计数）
  clips/               # 知识型的合成语音缓存
```

**不进安装目录**（安装目录只读），不进 git 仓库。

### 17.7 与规则层的关系

学习库是**介于规则层与模型层之间的一层**：

```
规则层（录音） → 命中即播，不变
     ↓ 未命中
学习库（学到的模板/知识） → 命中则直接重算或播缓存
     ↓ 未命中
模型层（实时调用）
```

**学习库永远不能覆盖规则层已成功回答的问题**，只在规则层答不上时生效。

### 17.8 已知风险

- **模糊匹配张冠李戴**：靠权重与事后标记收敛，不做事先确认
- **模板质量参差**：由用户赛后确认把关，未确认的不入库
- **结论写死**：模板里的条件化规则已尽可能消除，但无法完全排除；监控「标记错误率」，超过 30% 的模板类别应禁用

## 十八、测试要点

- **`query_class` 分类**：安全/分析/已知/未知四类的判定；`SAFETY` 优先于 `ANALYSIS` 的重叠词（「为什么被罚」）
- 三道校验闸各自的通过/拒绝用例（含伪造字段、编造数字、中文数字拒绝）
- **数字闸换算**：`83.512` ↔ 「1 分 23 秒 5」；比例值 ↔ 百分比；序数词
- 超时降级、非法 JSON 直降级（不重试）、限流降级、自适应降级（连续 3 次）
- 各档位接管范围（安全类硬拒绝在 A 档仍被拦截）
- 配置钳制：`timeout_s` 设 10 被钳到 2.0；`max_answer_chars` 设 200 被钳到 60
- 单飞约束：连续提问时旧请求被取消；模型等待期间 PTT 不被阻塞
- `DerivedTracker` 扩展后的圈记录：边界判定、两套有效圈判据、环形缓冲边界
- `SimTelemetry` 的圈推进模式（默认关闭时现有 132 项测试不受影响）
- 上下文组装的 token 上界、对手层只含 3 台
- 无 Key / 断网时原有功能完全不受影响
- 不同兼容性档位（无 JSON mode、无流式）下的降级路径
- **学习库模板校验**：白名单外字段、含函数调用的 `when`、缺兜底分支、填充后过不了数字闸——四类都必须拒绝入库
- **学习库权重**：标记错误 -2、连续错 2 次自动禁用、正确 +1
- **学习库不覆盖规则层**：规则层成功回答时绝不查询学习库
- 知识型与动态型分流：动态型成品答案不入库

### 上线前的量化门槛

- **数字闸误杀率**：用真实模型跑 50 条白名单问句，误杀率必须 **≤ 20%**
- **`SAFETY` 零漏放**：安全类问句在任何档位下都不得调用模型（用 30 条越界句验证）
- **学习库错误率**：上线后用 20 场数据观察，被标记错误率 > 30% 的模板类别应禁用
